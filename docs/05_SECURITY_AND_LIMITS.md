# 05 — Security, privacy and known limitations

**This is a portfolio prototype, not an audited financial product. Do not use real personal inboxes or launch a public Gmail service until the appropriate security, legal and Google-policy work is complete.**

## Important boundaries

- Public demo fixtures are fictional. Offline demo changes are browser-memory state; backend demo requests do not read or write a user's account. They are not proof of a real Gmail integration.
- When `FIREBASE_PROJECT_ID` is configured, Spring validates Firebase ID-token signature/issuer/audience/time/subject and requires a verified email. The backend uses the verified token subject, not a client-provided owner ID, for database queries. The included isolation tests use **mock JWTs**, not live Google/Firebase signatures. Tokens already issued are not checked against Firebase revocation/disabled-user state on each request; they can remain usable until expiry unless a proper revocation mechanism is added.
- JPA repository calls are scoped by owner, but database row-level security is **not** configured. Anyone with database credentials/admin access can access the underlying data. Secure the database/network/roles and the deployment account; minimize who can access backups and logs.
- On ordinary account import, the server processes pasted HTML in memory and stores extracted merchant/category/time/amounts, item tags, fee labels, source identifiers and account subject. It does not intentionally retain raw HTML or Google access/refresh tokens. A provider, proxy, browser, debugger, log configuration or backup could still retain sensitive data: inspect and control each before real use.
- The test Gmail scope grants broad read-only mailbox access at Google even though the implementation searches a limited subset. The token is sent to your test backend over HTTPS, used for that request and not intentionally stored; Google's authorization can persist until revoked. Real Gmail use remains disabled/unverified by default.
- User deletion removes Ranger ledger records from the configured database; it does **not** delete the Firebase Auth account, external logs, old exports, or backups, and signing out does not necessarily revoke Google permission. Establish a retention/deletion policy and actual contact before using the app with others.
- The local default H2 database is ephemeral. The container refuses its default H2 mode unless the owner explicitly overrides the guard for **demo-only** deployment. Neon profile uses TLS hostname verification, small Hikari pool and schema `validate`; secure backup and schema change management remain the operator's responsibility.
- The backend limits POST/PATCH bodies to 1 MiB before JSON parsing, restricts manual HTML to 100,000 characters, limits parser item/fee counts, uses fixed Google endpoints and bounded test responses, and does not execute submitted HTML. Input caps reduce risk but are **not** a complete DoS defense.
- API CORS uses explicit configured origins. CORS is a browser policy, **not** authentication. Never put database secrets or server keys in `VITE_*` variables; those are exposed to every browser. TLS is expected at the public host's edge.

## What still needs engineering before real users

1. Independent threat modeling and security review; provider policy/legal/privacy review; incident response and named owner. Replace the draft privacy page with environment-specific practices and contacts.
2. Rate limiting, anti-abuse/bot controls, account enumeration and credential stuffing mitigations, monitored security events, sensible quotas, backup/restore testing and secure log/retention controls. Add a deployment-specific CSP and test Google/Firebase popups and images against it.
3. Test **real** Firebase signatures, claims, email verification, sign-out/revocation, session expiry and two-account authorization. Test concurrent imports, database failure/recovery, explicit schema migrations, deletion and backups.
4. Confirm that Ranger's intended Gmail reporting use case is eligible under Google's approved-use policy; this is not established. Review Gmail's testing and production requirements with Google. Implement/verify an appropriate production token-verification design if the scope ever changes, and budget for any required assessment. Perform actual permission, denial, token expiry, tester isolation and revocation testing.
5. Add bounded pagination and server-side filtering rather than returning every receipt at once; load-test the free host, database and cold starts. A concurrency race can produce a database conflict rather than a friendly duplicate response; the owner/source unique constraint prevents duplicate rows, but concurrent behavior has not been load-tested.
6. Add richer receipt adapters with tests against consented and **redacted** examples, confidence/review tooling, manual correction of merchant/category/time/amount, refund/partial-cancel handling, currencies and reconciliation rules. Current correction only edits junk tags; a bad total must be deleted/re-imported from corrected supported HTML.

## Parser and metric limits

- Only supported HTML elements are parsed: `data-merchant` / `.merchant-name`, `data-total` / `.grand-total` / `.order-total` / `.total-paid` or certain total rows, optional `[data-item]` / `.item-line`, `[data-fee]` / `.fee-line`, and ISO-offset/Z order time. No PDF or attachment parsing, OCR, arbitrary bank statements, live investment prices, actual bank/merchant matching, automatic refunds, CSV export, multi-currency conversion or AI extraction is implemented. Unknown layouts can be skipped or misread; review every extracted result.
- The manual-import fallback time is the **import time** when no explicit time is recognized; Gmail's fallback is the email received time. Both are approximate, not necessarily when an order happened. Timezone options are a small predefined set and the preference is stored only in that browser.
- Backend amounts use `BigDecimal` and PostgreSQL `NUMERIC(12,2)` per value; the UI rounds to integer paise for its selected views. It is not a certified accounting ledger and very large aggregated UI totals should not be treated as audit-grade. A line without an item price is counted as unknown, not assigned a guessed amount.
- Fees commonly belong inside the order total, but unusual receipts may differ. Late-night, fee and junk categories overlap. Late-night totals cover all recorded non-investment categories, not exclusively food. Investment contributions are excluded from recorded spend.
- Stash calculations and comments are illustrative “what if” scenarios. They do not establish actual sleep/health, guarantees, gold prices or future returns and are not financial/medical advice.
- `GET /api/public/health` reports that the web application is running; it is not a continuous guarantee that Neon, Firebase or Gmail are healthy after startup. Client retry is bounded and can require a manual retry.

## Dependency hygiene

On 29 October 2026, `npm audit` reported zero known advisories for the installed frontend dependency tree; this is time-sensitive, covers only what the advisory database knew, and is not a security certification. `package.json` overrides `@grpc/grpc-js` to a patched 1.14.x version because the Firebase umbrella package also brings in an unused Firestore dependency with an older gRPC version. Ranger uses Firebase Auth, **not Firestore**. Re-evaluate that override and compatibility if you add Firestore or upgrade Firebase; do not assume the override makes a new Firestore integration tested. Review Java dependencies separately and rerun audits regularly.
